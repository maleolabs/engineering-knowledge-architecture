# EKA Reference Project

> Anchor EKA: Reference Implementation — a complete, conformant example repository demonstrating Engineering Knowledge in practice (Core v1.1 §8.1–8.3, P13, R10–R12).
> Convention document, not an artifact (no `type`/`id`). Companion to [project/README.md](project/README.md) (the project-facing README) and [../skeleton/docs/README.md](../skeleton/docs/README.md) (the conventions the project serializes).

## Purpose

The **EKA Reference Project** is an educational artifact: a complete, working EKA repository that shows what a real project looks like **when the standard is applied to engineering knowledge** — not when the standard is applied to its own specification.

The reference implementation repository (this repository) documents itself: standard texts, implementation ADRs, CLI documentation. That is meta-knowledge. The Reference Project is deliberately the opposite: an ordinary product with a universally understood domain — **Feather**, a markdown blogging platform — whose engineering knowledge is serialized exactly the way `eka init` would scaffold it, filled with realistic artifacts, and **validated clean (0 errors, 0 warnings)**.

What the Reference Project demonstrates:

- Every one of the 26 artifact tokens in use, in its home dimension, with its owned state vector.
- The five Engineering Domains as a working authority chain (Core §8.1): Discovery constrains Architecture, Architecture constrains Planning, and so on down to Operations.
- R10 (stratification traceability) satisfied for **every** non-Discovery artifact — zero warnings, by construction, not by luck.
- R12 (cross-stratum supersession prohibition) honored: no `supersedes`/`amends` anywhere in the project.
- P13 (lossless exchange) exercised live: export → import round-trip over the whole project.
- The operating layer in motion: one active container, work items in every execution state, tickets as pure projections, sessions and reviews recorded.

It is **not** a demonstration of software architecture complexity: the domain is intentionally trivial so the knowledge model, not the product, is what the reader studies.

## Knowledge Relationships Walkthrough

The authority chain **Discovery → Architecture → Planning → Execution → Operations** is not decoration — it is enforced by the relationship discipline (R10) and visible in the artifact pairs. Concrete walks:

**Discovery constrains Architecture.** `req:publishing-core` (approved, stratum 1) is the root of the chain: `adr:content-storage` derives from it, and `arc:feather-system` derives from it. A specification lower in the chain may not contradict these. Draft tolerance: `req:comments-phase2` stays draft until the MVP ships, so it constrains nothing yet.

**Research feeds decisions.** `fnd:markdown-editor-options` and `fnd:search-approach` (Discovery) are depended on by `adr:content-storage` and `adr:search-sqlite-fts` respectively — the accepted decisions cite the evidence that justifies them.

**Architecture constrains Planning.** `scp:mvp-v1` derives from `req:publishing-core` and `adr:content-storage`; `epc:authoring-experience` derives from the scope; `plan:roadmap-v1` derives from the scope and carries `phase: mvp`. The approved plan is the commitment that execution may not exceed.

**Planning constrains Execution.** Every work item and both containers depend on `plan:roadmap-v1:1` — the versioned reference form (`<type>:<id>:<instance-version>`). `ctr:wave-7` (active) locks the plan; `ctr:wave-6` (completed) shows the previous wave. Work items depend on the container and the plan, so "why does this work item exist?" walks: `sto:publish-post` → `ctr:wave-7` → `plan:roadmap-v1:1` → `scp:mvp-v1:1` → `req:publishing-core` (stratum 1).

**Execution feeds Operations.** `rel:v090` depends on `ctr:wave-6` and derives from the plan; the runbooks depend on `arc:feather-system`. The release record aggregates execution outcomes upward without quoting them (records README convention).

**R12 in practice.** No artifact in the project carries `supersedes` or `amends` — there is nothing to supersede yet, and nothing may ever target a higher stratum. When the first supersession happens (e.g. a future ADR replacing `adr:content-storage`), it will be same-stratum (Architecture → Architecture).

**Tickets and sessions are exempt by design.** `tkt-` (pure projections) and `ses-` (operating records) need no upward chain — they are shadows and notes, not knowledge claims (R10 exemptions).

## Integration Notes

- **How the docs reuse the project:** every claim about the standard ("the validator enforces R10 as a warning", "tickets are projections", "export is lossless") is demonstrated, not asserted, by pointing at `reference/project/` artifacts and the screenshots above. When a doc needs a real example of a token, state value, or relationship, it cites a Feather artifact instead of inventing a fragment.
- **Single source of screenshots:** all screenshots must originate from this project, per the checklist above. Never reuse screenshots from other contexts or other repositories.
- **Keeping it conformant:** the project is part of this repository, so `eka validate .` at the root covers it too. A change that breaks the Reference Project (any error or warning) breaks the repository-wide gate — this is intentional: the project must stay the living proof of the standard. The 8 ADR R10 warnings of `reference/decisions/` are unrelated to the project and remain the only warnings at root scope.
- **When the standard evolves:** if `skeleton/` changes (new conventions, new tokens), the project's `docs/` convention copies must be re-synced from the skeleton (exact copies, per the skeleton's template policy), and the artifacts re-validated. Artifact content evolves with the product story; convention files evolve only with the skeleton.
- **Educational use:** the project is intended as a teaching corpus — read it as the worked example of the [Engineering Operating Guide](../skeleton/docs/workflow-guide.md), one artifact per concept. It is also the recommended input for tool builders: `eka export` it, then verify an import target reproduces all 37 identities and states.
